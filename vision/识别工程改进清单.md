# 识别工程改进清单（落地 guandan-ai-coach 的经验）

来源：`竞品调研与经验借鉴.md` 里 `guandan-ai-coach` 踩过的坑——密集手牌时
"54帧只检出5帧"，靠**ROI切块加重叠(0.18→0.32) + 降置信度阈值**解决。
本文档记录：哪些已经落地到本仓库、怎么验证的、哪些是设计但还没写代码。

## 一、已实现并验证：可插拔引擎接口

**改动**：`guandan/engine_api.py`(新增) + `guandan/play.py::advise()` 重构 + `webapp/guandan.js` 同步镜像。

之前 `advise()` 内部硬编码 `from strategy_v2 import lead_v2, follow_v2`，想换引擎得改这个函数。
现在 `advise(..., engine="v2_plan")`，引擎通过注册表切换，调用方（`vision/recognize.py`、
前端 `camera.html`）完全不用改。以后接 DanZero+/rlcard 训练出的策略、或"贝叶斯猜牌+残局
Minimax"，只要：
```python
# Python
from engine_api import register_engine
register_engine("danzero_plus", lambda: MyRLEngine())
advise(hand, current, level, engine="danzero_plus")
```
```js
// JS(浏览器)
Guandan.registerEngine("danzero_plus", {lead(hand,level,ctx){...}, follow(hand,current,level,ctx){...}});
advise(hand, current, level, {engine: "danzero_plus"});
```

**验证**（真实跑过，不是猜测）：
- Python: `guandan/test_core.py` 29/29 通过；`play.py` 200局自我对弈全部收敛；
  `compare.py`(V1 vs V2 对打400局的既有脚本) 跑分不变；手动调用 `advise(..., engine="v1_heuristic")`
  确认能正常切换、且不传 `engine` 时行为与改动前逐字一致。
- JS: `webapp/test.js` 扩到 32/32 通过，新增用例覆盖：默认引擎不传时行为不变(向后兼容)、
  显式切 `v1_heuristic`、未知引擎名报错、`registerEngine` 注入自定义对象引擎直接生效。

## 二、已实现：网页端 ROI 切块检测（精细模式）

**改动**：`webapp/camera.html`——`preprocess()`/新增`detectRaw()`/`drawAndExtract()`/
`computeTiles()`/`detectTiled()`，UI 加了「🔍 精细模式」按钮（默认关闭）。

**做法**：默认关闭时行为和改动前逐字节一致（回归安全）。打开后：把画面横向切成
**3 块、重叠 30%**（手牌是横向展开的扇形，横切最贴合），每块单独喂给模型（角标不会被
压缩到几像素），检测框换算回整帧坐标后合并，最后统一做一次全局 NMS 去重——
这样同一张牌被两块都检测到时不会重复计数，骑缝的牌至少被一块检测到就不会丢。

**验证方式（如实说明，没有条件跑真实浏览器+摄像头+模型）**：
- 环境限制：这个沙箱没有显示器/摄像头，无法真正打开 camera.html 用真手机摄像头实测。
- 已验证的部分：
  1. `node --check` 语法检查通过；
  2. 切块几何公式单独用 Node 验证：多种分辨率(800/1280/1920px)下，3块能**完整覆盖整个画面宽度、
     相邻块正确重叠、无缝隙**；
  3. 用模拟的检测框验证合并逻辑：**同一张牌被两块重复检出**(坐标略有偏差) → 全局NMS后**合并为1个**；
     **紧挨着的两张不同牌** → NMS后**都保留**；**骑缝牌只被一块检出** → **仍保留**。
- ⚠️ **务必让用户在真机上实测**：真实摄像头画面的光照、镜头畸变、手抖动比模拟场景复杂，
  拿到 4090/手机后应实际打开「精细模式」对比开关前后的识别数量，再调 `TILE_COLS`/`TILE_OVERLAP`。

## 三、设计但未实现：牌局状态机（下一步，Phase 2）

这是更大的功能（连续视频→"谁出过什么牌"→喂给引擎），按项目规范**不做半成品**，
先把设计定下来，等真正开始做"连续视频跟踪"时直接按这份规格实现：

### 现状
`camera.html` 现在的 `accum`(Map) 是最简单的"单帧最大计数"累加器：不区分"这是我的手牌"
还是"这是桌面上刚打出的牌"，也没有"新一轮开始"的概念，只适合当前"扫一遍手牌拍照识别"的用法。

### 目标状态机（下一步实现时的规格）
```
两个独立累加区（不是一个 accum，是 handAccum + tableAccum）：
  - handAccum：我的手牌。单调累加(现有 accum 逻辑不变)，因为手牌在整个回合内基本不变。
  - tableAccum：本轮桌面上"刚打出的牌"。规则：
      · 检测到的牌型与上一次记录的不同 且 持续 N(=3) 帧稳定 → 判定"新的一手已打出"，
        触发 played_history.push(上一手)，tableAccum 清空重来。
      · 若之前打出的牌连续 M(=10) 帧没再检测到(牌已被收走/翻过去) → 允许清空,不影响 handAccum。
  - 手牌区/桌面区用画面位置区分：出牌区通常在画面中央/桌面，手牌区在下方/近摄像头处——
    简单版可以让用户框一次 ROI(点两下取矩形)，复杂版用检测框的 y 坐标做启发式分区。
```

### 对应的引擎侧改动（已经预留好接口，不用等状态机写完）
`GameContext.played_history` / `GameContext.seat_hand_sizes` 字段已经加在
`engine_api.py` 的 `GameContext` 里了——状态机做好之后，往这两个字段填数据，
`advise()`/前端调用点完全不用再改。

### 优先级
先在真实设备上验证「精细模式」切块检测的识别率提升，再决定是否要上状态机——
如果单张识别已经够准，练习/复盘场景下"扫一遍→给建议"可能就够用，不一定非要做成实时连续视频。
